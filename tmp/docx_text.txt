Fișierul Excel/CSV pe care l-am construit este mai bogat decât tabelul chart_of_accounts din Finguard. El nu conține doar conturi contabile, ci și:
REPORT_GROUP        = rânduri de raportare / agregare
ACCOUNT_GROUP       = conturi sintetice
ACCOUNT_LEAF        = conturi finale pentru calcul
CALCULATED          = indicatori calculați
INTERNAL_ANALYTIC   = analitice interne de raportare
De aceea, nu trebuie importat tot Excel-ul direct în chart_of_accounts. Corect este să îl împarți pe mai multe destinații.

Tabelele Finguard existente acoperă o parte din această logică, dar nu pe toată.
2. Ce intră în chart_of_accounts
În chart_of_accounts trebuie importate doar rândurile care reprezintă conturi reale sau conturi de raportare contabile:
ACCOUNT_GROUP
ACCOUNT_LEAF
Opțional, poți importa și:
INTERNAL_ANALYTIC
dar numai dacă vrei ca analiticele interne de tip 665.01, 765.01 etc. să existe explicit în planul de conturi al aplicației.
Nu trebuie importate în chart_of_accounts:
REPORT_GROUP
CALCULATED
rânduri de tip EBITDA
rânduri de tip EBIT
Profit brut
Profit net
% marje
Încasări totale
Plăți totale
Sold numerar început/final
Acestea nu sunt conturi contabile, ci linii de raportare sau indicatori calculați.

4. Problemă importantă în schema actuală
Tabelul chart_of_accounts nu are coloane pentru:
normal_balance
report_sign
statement_type
report_area
row_type
is_leaf_for_calculation
formula_or_rule
display_order
Aceste informații există în Excel și sunt importante pentru rapoarte.
Dacă le pierzi la import, aplicația va ști contul, dar nu va ști suficient de bine:

dacă se adună sau se scade;
dacă este cont leaf sau grup;

De aceea, recomandarea corectă este să nu forțezi totul în chart_of_accounts.
5. Recomandare tehnică: adaugă un tabel de layout / report definitions
Aș adăuga un tabel separat, de exemplu:
CREATE TABLE public.statement_line_definitions (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    company_id UUID REFERENCES public.companies(id) ON DELETE CASCADE,
    statement_type VARCHAR(50) NOT NULL
        CHECK (statement_type IN ('balance_sheet', 'income_statement', 'cash_flow')),
    line_key VARCHAR(150) NOT NULL,
    parent_line_key VARCHAR(150),
    display_name VARCHAR(255) NOT NULL,
    report_area VARCHAR(100),
    section_l1 VARCHAR(255),
    section_l2 VARCHAR(255),
    section_l3 VARCHAR(255),
    section_l4 VARCHAR(255),
    account_code VARCHAR(20),
    chart_account_id UUID REFERENCES public.chart_of_accounts(id),
    row_type VARCHAR(50) NOT NULL
        CHECK (row_type IN ('REPORT_GROUP', 'ACCOUNT_GROUP', 'ACCOUNT_LEAF', 'CALCULATED', 'INTERNAL_ANALYTIC')),
    normal_balance VARCHAR(20),
    report_sign VARCHAR(20)
        CHECK (report_sign IN ('+', '-', 'calculated')),
    is_leaf_for_calculation BOOLEAN NOT NULL DEFAULT FALSE,
    formula_or_rule TEXT,
    display_order INT NOT NULL DEFAULT 0,
    is_active BOOLEAN NOT NULL DEFAULT TRUE,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    UNIQUE (company_id, statement_type, line_key)
);
Acest tabel devine „scheletul” rapoartelor.
Excel-ul tău se potrivește aproape perfect cu acest tabel.

7. account_mappings
Tabelul account_mappings nu se populează direct doar din Excel.
El se populează după ce ai deja:
1. conturile din balanță în trial_balance_accounts;
2. conturile standard în chart_of_accounts;
3. regula de mapare.
Regulă recomandată:
trial_balance_accounts.account_code = chart_of_accounts.account_code
Dacă există potrivire exactă, creezi mapare 100%:
allocation_pct = 1.0
valid_from = period_start sau CURRENT_DATE
valid_to = NULL
Pentru conturile unde ai split allocation:
un cont din balanță poate merge către 2 sau mai multe conturi CoA
suma allocation_pct trebuie să fie maxim 1.0
Exemplu:
TB account 628 = Alte servicii executate de terți
70% → OPEX / servicii executate de terți
30% → cheltuieli nerecurente, dacă utilizatorul decide această reclasificare

10. income_statement_lines
Aici apare o mică problemă în schema actuală.
Tabelul are:
category VARCHAR(100) NOT NULL CHECK (category IN ('venituri', 'cheltuieli'))
Dar în imaginile tale apar și rânduri de tip:
Rezultat operațional brut
% Marja operațională brută
Rezultat operațional din activitate recurentă
% Marja operațională din activitatea recurentă
EBITDA
% Marja EBITDA
EBIT
% Marja EBIT
Rezultat financiar
Profit brut
Profit net
% Marja profit net
Acestea nu sunt nici venituri, nici cheltuieli. Sunt rânduri calculate.
Recomand să modifici constraint-ul:
CHECK (category IN ('venituri', 'cheltuieli', 'rezultat', 'marja', 'calculated'))
Ideal, adaugi și o coloană:
line_type VARCHAR(50)
CHECK (line_type IN ('account', 'group', 'calculated', 'kpi'))
Altfel, aplicația va forța indicatorii calculați într-o categorie greșită.
11. cash_flow_lines
Pentru cash-flow, schema actuală este prea simplă:
section CHECK (section IN ('operating', 'investing', 'financing'))
Dar în imaginile tale apar și:
Sold numerar la început de perioadă
Încasări totale
Plăți totale
Plăți neobișnuite
Încasări neobișnuite
Viramente interne
Sold numerar la final perioadă
Acestea nu intră curat doar în:
operating
investing
financing
Recomand să extinzi secțiunea:
CHECK (section IN (
    'opening_cash',
    'operating',
    'investing',
    'financing',
    'internal_transfers',
    'unusual',
    'closing_cash',
    'calculated'
))
Sau, mai bine, păstrezi section pentru nivelul principal și adaugi:
cash_flow_area VARCHAR(100)
line_type VARCHAR(50)
Pentru cash-flow, mai ai nevoie și de reguli de calcul.
12. Atenție majoră: cash-flow direct nu se poate calcula perfect doar din balanță
Structura din imagini este de tip cash-flow direct:
Încasări din clienți
Plăți către furnizori
Plăți salarii
Plăți taxe
Încasări din dobânzi
Plăți dobânzi
Plăți pentru investiții
Pentru acest tip de raport, aplicația are nevoie de rulaje cu contrapartidă:
5121 / 5311 contra 4111
5121 / 5311 contra 401
5121 / 5311 contra 421
5121 / 5311 contra 4423
etc.
Dacă aplicația are doar balanța de verificare, fără jurnal contabil sau registru de casă/bancă cu contrapartidă, atunci cash-flow-ul direct poate fi doar aproximat.
Pentru cash-flow exact, ai nevoie de unul din următoarele:
1. jurnal contabil cu debit / credit / cont corespondent;
2. registru bancă + casă;
3. rulaje pe corespondențe;
4. export contabil detaliat, nu doar balanță sintetică.
Balanța simplă îți dă solduri și rulaje, dar nu îți spune întotdeauna clar cui s-au făcut plățile sau de la cine s-au primit încasările.
13. Recomandare pentru Cash Flow: tabel separat de reguli
Aș adăuga un tabel:
CREATE TABLE public.cash_flow_mapping_rules (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    company_id UUID REFERENCES public.companies(id) ON DELETE CASCADE,
    line_key VARCHAR(150) NOT NULL,
    description VARCHAR(255) NOT NULL,
    cash_flow_direction VARCHAR(30) NOT NULL
        CHECK (cash_flow_direction IN ('opening', 'inflow', 'outflow', 'closing', 'internal_transfer')),
    section VARCHAR(50) NOT NULL
        CHECK (section IN ('operating', 'investing', 'financing', 'unusual', 'internal_transfers', 'cash_balance')),
    cash_account_prefixes TEXT[] NOT NULL DEFAULT ARRAY['5121','5124','5311','5314'],
    counterparty_account_prefixes TEXT[],
    report_sign VARCHAR(20) NOT NULL DEFAULT '+'
        CHECK (report_sign IN ('+', '-', 'calculated')),
    display_order INT NOT NULL DEFAULT 0,
    formula_or_rule TEXT,
    is_active BOOLEAN NOT NULL DEFAULT TRUE,
    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    UNIQUE (company_id, line_key)
);
Exemplu de regulă:
line_key: cf.receipts.operating.customers
description: Încasări din Clienți
cash_flow_direction: inflow
section: operating
cash_account_prefixes: 5121, 5124, 5311, 5314
counterparty_account_prefixes: 411, 4111, 413, 418
Alt exemplu:
line_key: cf.payments.operating.suppliers
description: Plăți pentru Furnizori
cash_flow_direction: outflow
section: operating
counterparty_account_prefixes: 401, 403, 408

16. Fluxul corect de implementare în aplicație
Ordinea recomandată este:
1. Import Excel / CSV template
2. Creează chart_of_accounts pentru conturile reale
3. Creează statement_line_definitions pentru toate liniile de raportare
4. Creează cash_flow_mapping_rules pentru liniile de cash-flow
5. Importă balanța de verificare
6. Creează account_mappings între trial_balance_accounts și chart_of_accounts
7. Verifică dacă maparea este 100%
8. Generează financial_statements
9. Generează balance_sheet_lines
10. Generează income_statement_lines
11. Generează cash_flow_lines
12. Calculează kpi_values
13. Generează reports
17. Concluzia practică
Fișierul Excel se poate adapta foarte bine la Finguard, dar nu trebuie tratat ca un simplu chart_of_accounts.
Structura corectă este:
chart_of_accounts
= doar conturile contabile reale
statement_line_definitions
= structura completă de raportare din Excel
account_mappings
= legătura dintre balanță și conturile CoA
financial_statements
= raportul generat pentru o perioadă
balance_sheet_lines
income_statement_lines
cash_flow_lines
= rezultatele calculate
kpi_definitions
kpi_values
= indicatorii calculați
cash_flow_mapping_rules
= regulile speciale pentru cash-flow
Cea mai importantă ajustare este să introduci un tabel de tip statement_line_definitions. Fără el, vei forța în chart_of_accounts rânduri care nu sunt conturi contabile, precum EBITDA, EBIT, Profit net, Total active, Total datorii sau Sold numerar final.
